# SNS投稿パイプライン 実行指示書（compose step・エージェント共通）

あなたはSNS投稿パイプラインの実行エージェントである（Claude Code / Codex いずれでもよい）。
テーマ別に、素材案（参考元）から SNS 投稿の下書き（本文3種＋参考画像）を作り、テーマ専用の投稿管理テーブルへ登録する。
以下の手順を上から順に、過不足なく実行すること。

> **ランタイムの場所**: 設定・状態・テーマ定義は `SNS_PIPELINE_HOME`（未設定なら `~/.sns-pipeline`）配下にある。
> 以降このディレクトリを `$HOME_DIR` と書く。ここは配布物（プラグイン）とは別で、各テナントの実データが入る。

---

## 0. 絶対ルール（全手順に優先）

1. Lark操作は必ず `lark-cli --profile <cfg.PROFILE> <command> --as bot`（Base書込）と、チャット読取用の識別（`cfg.CHAT_PROFILE` / `--as <cfg.CHAT_IDENTITY>`）で実行する。プロファイルは `$HOME_DIR/config.json` の値に従う。
2. 書込先は config の `TABLE_ID_SOURCES`（参考元・全テーマ共通）と、各テーマの `TABLE_ID_POSTS`（投稿管理・テーマ別）のみ。レコード削除、テーブル・フィールド・ビューの変更はしない。
3. **投稿本文（手順4）の入力は、参考元レコードの「要約」フィールドの内容と、そのテーマの `BACKBONE_FILE`（背景・思想）に書かれた内容のみ。** 要約に無い事実・数値・固有名詞（バックボーンに明記されたもの以外）を足さない。元URLへの再アクセス、「元テキスト」フィールドの直接引用は禁止。
4. **すべての投稿は「読み手の教育 → 問い合わせへの誘導」を目的に書く（手順4）。** テーマごとの読者・ゴール・誘導先・語り口は config の各テーマ設定と `BACKBONE_FILE` に従う。
5. 1ランの上限: 分析（手順2）は全テーマ合計で最大5件、投稿作成（手順4〜6）は **テーマごとに最大 `PACE.POSTS_PER_THEME_MAX`（既定1）件**。対象が無いテーマは0件で正常終了する。
6. ログ・本文・タイトル・備考に装飾目的の絵文字を使わない。
7. コマンド失敗時の再試行は同一コマンドにつき1回まで。それでも失敗したらその対象をスキップしログに記録し次へ。ラン全体を止めるのは設定未完了（手順1）のときのみ。
8. 対話的確認はできない前提で動く。迷う場合は安全側（書き込まない・スキップしてログに残す）を選ぶ。

## 1. 設定読込と事前チェック

1. `cat $HOME_DIR/config.json` を読み、`PROFILE` / `CHAT_PROFILE` / `CHAT_IDENTITY` / `BASE_TOKEN` / `TABLE_ID_SOURCES` / `THEMES`（各要素の `THEME_KEY` `NAME` `ENABLED` `CHAT_ID` `TABLE_ID_POSTS` `READER` `GOAL` `CTA_URL` `CTA_STYLE` `BACKBONE_FILE` `IMAGE_TASTE_FILE` `LOGO_FILE`）を取得する。
   - `BASE_TOKEN` / `TABLE_ID_SOURCES` が空、または有効な `THEMES`（`ENABLED != false` かつ `CHAT_ID` と `TABLE_ID_POSTS` が非空）が0件なら、手順7の形式でログに「設定未完了」と記録し、標準出力に `SKIP: config incomplete` と出して終了する（エラー扱いにしない）。
2. `mkdir -p $HOME_DIR/images $HOME_DIR/logs $HOME_DIR/tmp` を実行する。
3. フィールド構成を確認する（このランで初回のLark読取を兼ねる）:
   ```bash
   lark-cli --profile <cfg.PROFILE> base +field-list --base-token "$BASE_TOKEN" --table-id "$TABLE_ID_SOURCES" --as bot
   # 各テーマの TABLE_ID_POSTS についても field-list を実行
   ```
   参考元に「タイトル / 種別 / テーマ / URL / 元テキスト / 要約 / 分析ステータス / 取込元メッセージID / 投稿者名 / メッセージ投稿日時 / 取込日時 / 使用状況 / エラー詳細」、各投稿管理テーブルに「タイトル / 本文（Instagram）/ 本文（Threads）/ 本文（X）/ 投稿済（Instagram/Threads/X）/ 画像 / 参照元 / 画像プロンプト / 作成日時 / 備考」があることを確認する。「投稿済（〜）」の3チェックボックスは人の確認・記録専用で、パイプラインからは書き込まない。欠落があればログに記録して終了する。

## 2. 未分析レコードの取得と分析（全テーマ横断・合計最大5件）

### 2-1. 対象取得
```bash
lark-cli --profile <cfg.PROFILE> base +record-list \
  --base-token "$BASE_TOKEN" --table-id "$TABLE_ID_SOURCES" \
  --filter-json '{"logic":"and","conditions":[["分析ステータス","==","未分析"]]}' \
  --sort-json '[{"field":"取込日時","desc":false}]' \
  --limit 5 --format json --as bot
```
- filter-json がエラーになる場合: `--filter-json` を外して最大50件取得し、応答から「分析ステータス=未分析」を古い順に最大5件抽出する。
- 0件なら手順3へ。

### 2-2. 分析（要約の作成）
各レコード（record_id を控える）について:
- **「テーマ」フィールドの値を確認し、そのテーマの `BACKBONE_FILE` を読んでから要約する。** 同じ記事でも、テーマの読者に引き寄せて拾う論点が変わる。
- **足切り**: 用途説明・運用連絡（「〜用です」等）、挨拶・相槌だけ、社外に出せない内部情報 → 要約せず「分析ステータス」を `対象外` にし「エラー詳細」に理由を書いて次へ。
- 種別=URL記事: URLの本文を取得して要約する。ホストが `*.larksuite.com` / `*.feishu.cn` の場合は Playwright ではなく `lark-cli docs +fetch --doc "<URL>" --doc-format markdown --as user` で取得する。取得不能ならエラー処理。
- 種別=コメント: 「元テキスト」を要約の起点にする。
- 要約は300〜500字。事実・論点・そのテーマにとっての意味を書く。要約を「要約」フィールドへ書き、分析ステータスを `分析済` に更新する。失敗時は `エラー` にして「エラー詳細」を記録する。

## 3. 投稿対象の選定（テーマごとに最大 POSTS_PER_THEME_MAX 件）
```bash
lark-cli --profile <cfg.PROFILE> base +record-list \
  --base-token "$BASE_TOKEN" --table-id "$TABLE_ID_SOURCES" \
  --filter-json '{"logic":"and","conditions":[["分析ステータス","==","分析済"],["使用状況","==","未使用"]]}' \
  --sort-json '[{"field":"取込日時","desc":false}]' \
  --limit 30 --format json --as bot
```
- 取得結果を「テーマ」で群に仕分け、**各テーマから取込日時が古い順に最大 `POSTS_PER_THEME_MAX`（既定1）件**を選ぶ。1テーマから上限を超えて選ばない。
- どのテーマも0件なら「作成対象なし」とログに記録し手順7へ。
- 以降の手順4〜6は、選んだレコードごとに、そのテーマの設定・`BACKBONE_FILE`・`IMAGE_TASTE_FILE` を適用して実行する。テーマが違う投稿を同じ方針・同じ画像テイストで作らない。

## 4. 投稿本文の作成（SNS別3種・入力は「要約」＋バックボーンのみ）

選んだ各レコード（=1投稿テーマ）について、Instagram / Threads / X の本文を個別に作る。

### 4-1. 記事骨格（教育 → 誘導・全テーマ共通）
本文は次の4ブロックの順で構成する（ブロック名は本文に書かない）。
1. **気づき** — 読者が薄々感じているが言語化できていない課題を、読者の言葉に近い形で提示。「自分のことだ」と思わせる。
2. **教育（中心・最も長い）** — なぜそうなるのか、どう見分けるのか、何を基準に判断すべきかを渡す。読むだけで一つ賢くなる密度。ノウハウ列挙でなく「考え方」を残す。
3. **橋渡し** — その考え方をこの事業がどう実践/支援しているかを一言で（自慢でなく立ち位置の説明）。
4. **誘導** — 次の一歩を1つだけ示す。複数行動を並べない。

**分量の目安は 気づき1：教育7：橋渡し1：誘導1。** 教育が最も長い状態を必ず保つ。売り込みが教育を上回ったら書き直す。

### 4-2. 共通ルール
- 入力: そのレコードの「要約」＋そのテーマの `BACKBONE_FILE` のみ（絶対ルール3）。
- 語り口・禁止事項は `BACKBONE_FILE` に従う。読者は config の `READER`、ゴールは `GOAL`。
- **本文にURLを貼らない。** 誘導は config の `CTA_STYLE`（既定「プロフィールのリンクから」）の表現で行う。参照元はBaseのリンクで管理する。
- 煽らない・根拠のない効果訴求をしない・要約に無い事実を足さない・装飾絵文字を使わない。

### 4-3. SNS別の書き分け
| SNS | 文字数 | 構成 |
|---|---|---|
| Instagram | 300〜600字 | 冒頭125字で「気づき」を完結させ続きを読ませる。以降で教育を改行多めに展開、橋渡し・誘導を末尾に短く。末尾にハッシュタグ5〜10個（テーマに合うもの＋テーマ固有）。 |
| Threads | 500字以内 | 会話調。教育の論点を1つに絞る。問いかけで終えて返信を誘ってよいが誘導の一文は残す。ハッシュタグ0〜1個。 |
| X | 全角140字以内（超過厳禁） | 教育の一点だけを鋭く。冒頭で結論、ハッシュタグ1〜2個。字数の都合で誘導が入らなければ誘導は省いてよい（教育を削らない）。書いた後に必ず文字数を数える。 |

- 投稿管理用「タイトル」（30字以内・3SNS共通）も作る。
- **完成後セルフチェック（1つでも×なら書き直す）**: ①教育が最も長い ②読者が判断基準を1つ持ち帰れる（一般論で終わっていない）③誘導が1つでゴールを向く ④バックボーンの禁止事項に触れていない。

## 5. 参考画像の生成（画像生成モデルのみ・HTML合成は禁止）

> **絶対ルール**: 投稿画像は**画像生成モデル（Codexの image_gen 等）だけで文字・ロゴまで完結させる**。HTML/CSS/SVG/Canvas/スクリーンショット等の組版・合成は一切しない。「文字が崩れるかも」を理由に組版で代替しない。生成後にモデル自身へ確認させ、崩れがあれば再生成させる。

### 5-0. テーマ別ビジュアル（IMAGE_TASTE_FILE を読む）
そのテーマの `IMAGE_TASTE_FILE` を読み、`MODE` に従ってテイストを決める:
- `MODE: description` … PALETTE / MOOD / MOTIFS / PEOPLE / TYPOGRAPHY / FORBID の記述をそのまま使う。
- `MODE: image` … `REFERENCE` の画像（`$HOME_DIR/themes/<key>/image_refs/…`）を**参照画像としてCodexに渡し**、絵柄・彩度・質感を合わせさせる。あわせてPALETTE等の記述も使う。
- `MODE: instagram_url` … `REFERENCE` のURLの世界観に寄せる。自動ランでブラウザを開けない場合は、`IMAGE_TASTE_FILE` に書き写された PALETTE / MOOD / MOTIFS 等の記述を正とする（テイストは設定時に文章化済みである前提。未記入なら description 相当で進める）。
- **ロゴ**: config の `LOGO_FILE` が設定されていれば、その実ファイルを参照画像としてCodexに渡し**忠実に描かせる**（文字で社名を書いて代用しない・テーマ配色に合わせて描き替えない）。空なら省略。
- アスペクト比は 4:5（1080x1350）を既定とする。既定は1枚完結。複数枚は内容が本当に要求するときだけ。

### 5-0-1. 「AI生成っぽさ」の排除（品質の分岐点）
- アイコンは**定番ピクトグラムのみ**（虫眼鏡=調べる、歯車=整理、電球=ひらめき、握手=信頼 等）。意味を考えないと伝わらない比喩アイコンは禁止。
- アイコンは同一線幅・単色フラットで統一。グラデ・影・光沢・水彩タッチをアイコンに使わない。
- 見出し・本文の文字は装飾効果なしのフラットな単色。
- 生成後にズームして、線の不揃い・文字のにじみ・装飾効果を確認し、満たさなければ再生成する。

### 5-0-2. フレームワーク・ローテーション（同じテイストを直近10件で重複させない・最重要）
> **「骨格が同じでアイコンや文言を差し替えているだけ」を防ぐため、直近10件で同じフレームワークを繰り返さない。骨格そのものを毎回変える。ローテーションはテーマごとに独立管理する。**

手順:
1. `cat $HOME_DIR/themes/<key>/design_framework_log.json` を読み、`history` の直近10件（無ければ全件）に登場したフレームワークコード（A〜J）を確認する。**他テーマの履歴は見ない。**
2. 下表から、**このテーマの直近10件に登場していないコード**を1つ選ぶ（複数候補があれば最も長く未使用のもの）。全10種が直近10件で使い切られている場合のみ最も古いものを選び直す。
3. 選んだ骨格の説明を、Codexへの指示文の「構成」部分として使う（骨格を厳守・他骨格の要素を混ぜない）。背景・配色・モチーフ・人物は 5-0（IMAGE_TASTE_FILE）で上書きする。
4. 生成・保存・登録が完了したら、`design_framework_log.json` の `history` に `{"date":"<YYYY-MM-DD>","framework":"<コード>","title":"<投稿タイトル>"}` を末尾追記する（既存は変更しない）。ファイルが無ければ `{"_readme":"...","history":[]}` を作ってから進める。

| コード | 名称 | 骨格 |
|---|---|---|
| A | カードオーバーレイ型 | 背景全面に地の装飾、中央に角丸パネルを重ね、ロゴ→ラベル→見出し→説明→アイコン行→帯→フッターを縦に積む |
| B | ツートン分割型 | 画面を上下2分割。上30〜40%は濃色ソリッドに白抜き大見出し、下は淡背景にアイコン行・詳細・フッター |
| C | フルブリード・ポスター型 | カードなし。背景全面のイラストに半透明の色帯を敷き一言コピーを大きく載せる。情報量少なめ、ロゴは隅に小さく |
| D | パンチライン（引用）型 | 大きな引用符と共にメッセージを中央に1つ大きく。背景は単色ウォッシュ。下部に短い補足＋帯＋フッター |
| E | 左右比較（対比）型 | 画面を左右2カラムに分け、それぞれ見出し・アイコン・短い説明で対比。上部に全体見出し、下部に帯＋フッター |
| F | 縦積みナンバーリスト型 | 01/02/03… の大きな番号ブロックを縦に積む（雑誌特集風）。各項目は独立した大きめブロック |
| G | ビッグナンバー・フォーカス型 | 核となる数字・キーワード1つを視覚的中心に大きく置き、周囲に短い補足。要素点数少なめ |
| H | 縦ロードマップ型 | 縦に伸びる経路線（停車点のような表現）を主役ビジュアルにし、線に沿ってステップを配置 |
| I | フレームレス・タイポグラフィ型 | 淡背景中心。縁取り・装飾を最小限にし、文字サイズ・太さの強弱だけで階層を作るミニマル構成 |
| J | ボーダーフレーム型 | 画面四辺に太い縁取りを置き、内側に情報を配置する雑誌表紙のような構成 |

### 5-1. 実行手順
1. `codex exec --help` で使うフラグ（`--skip-git-repo-check` / `-C` / `-s` / `-o`）を確認する。
2. 枚数を決める（既定1枚）。5-0-2でフレームワークを選ぶ。5-0でテイストとロゴを確定する。
3. Codex（画像生成モデル）へ、1回の `codex exec` で下記を渡して生成する。**プロンプトには次を必ず含める**:
   - 「画像生成モデル（image_gen）を必ず使用。HTML/CSS/SVG/Canvas/スクリーンショットでの文字合成・組版は禁止。文字もロゴもすべて画像生成モデルに描かせる。」
   - アスペクト比4:5。5-0で決めた PALETTE / MOOD / MOTIFS / PEOPLE / TYPOGRAPHY / FORBID。
   - 「構成」= 5-0-2で選んだ骨格の説明。
   - 参照画像: `LOGO_FILE`（あれば）と、`MODE=image` の参照画像。渡した画像は忠実に再現させる。
   - 「日本語テキストは一字一句正確に。生成後に自分で確認し、文字崩れ・誤字・レイアウト破綻・情報不足があれば最大3回まで再生成して直す。」
   - 保存先 `images/post_<YYYYMMDD_HHMMSS>_1.png`（複数は _2, _3）。最後に保存した絶対パスだけ出力させる。
   > Codexへのプロンプトには、テナントにデザイン規範ファイルがあればその絶対パスを渡して着手前に読ませる（装飾絵文字を使わない・見出しの孤立改行を避ける・コントラストを十分に取る等を静止画像にも適用させる。タップターゲット等のWeb固有指標は対象外と明記）。
4. `ls -la $HOME_DIR/images/` で枚数分できたことを確認する。不足は1回だけ再実行。0枚なら画像なしで続行し備考とログに「画像生成失敗」と記録する。
5. 生成画像を開いて目視確認する（誤字・ロゴ欠落/文字代用・配色逸脱・情報密度・選んだ骨格になっているか）。問題があれば手順3からやり直す。
6. `design_framework_log.json` に今回のフレームワークを追記する（5-0-2手順4）。忘れると次回のローテーションが機能しない。

## 6. 投稿管理テーブルへの登録（そのテーマの TABLE_ID_POSTS へ）

### (0) 重複チェック（冪等性）
そのテーマの `TABLE_ID_POSTS` を「備考」に `参考元: <参考元record_id>` を含む行が無いか確認する。あれば作成済みとしてスキップ。

### (1) 投稿レコード作成
```bash
lark-cli --profile <cfg.PROFILE> base +record-upsert \
  --base-token "$BASE_TOKEN" --table-id "<そのテーマの TABLE_ID_POSTS>" \
  --json '{"タイトル":"<タイトル>","本文（Instagram）":"<...>","本文（Threads）":"<...>","本文（X）":"<...>","参照元":[{"id":"<参考元record_id>"}],"画像プロンプト":"<使用プロンプト全文。失敗時は空>","作成日時":"<YYYY-MM-DD HH:MM:SS>","備考":"参考元: <参考元record_id>。画像<N>枚・フレームワーク<コード>。<特記>"}' \
  --format json --as bot
```
- 投稿管理テーブルはテーマ別なので「テーマ」フィールドは不要（テーブル自体がテーマを表す）。
- 「備考」先頭に必ず `参考元: <record_id>` を入れる（(0)の突合キー）。
- 「参照元」でリンク形式エラーが出たら値を `["<record_id>"]` に変えて1回だけ再試行。それでも失敗ならキーを外して作成し備考に「参照元: <record_id>（リンク書込失敗）」と明記。
- 応答から新規 record_id を控える。

### (2) 画像添付（画像が生成できた場合のみ・枚数分）
```bash
cd $HOME_DIR && lark-cli --profile <cfg.PROFILE> base +record-upload-attachment \
  --base-token "$BASE_TOKEN" --table-id "<TABLE_ID_POSTS>" --record-id "<新規record_id>" \
  --field-name "画像" --file "./images/post_<...>.png" --as bot
```
（`--file` は相対パス必須。`cd $HOME_DIR` してから `./images/...` を渡す）

### (3) 参考元の使用済更新
参考元レコードの「使用状況」を `使用済` に更新する。

## 7. 実行ログの記録
`$HOME_DIR/logs/compose_YYYYMMDD.md`（当日・既存なら追記）へ:
